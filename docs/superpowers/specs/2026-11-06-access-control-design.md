# Контроль доступа и статистика использования — дизайн

Дата: 2026-11-06. Статус: согласован в чате, ждёт вычитки владельцем.

## Зачем

Бота хотят раздавать неопределённому числу людей, а запросы к LLM (OpenRouter) платные.
Нужно, чтобы:

- чужой человек не мог потратить деньги владельца без его явного одобрения;
- владелец всегда видел, кто сколько потратил (запросы, токены, $);
- владелец **не видел, что именно присылают другие** (приватность).

Критерий успеха: незнакомец без клика владельца не делает ни одного платного вызова; по
`/stats` видно расход по людям и периодам; содержимое чужих запросов не хранится и не
пишется в логи.

## Решения (согласованы)

| Вопрос | Решение |
|---|---|
| Лимиты для одобренных | **Нет** (вариант A). Только одобрение + ручной отзыв. Схема данных позволит добавить лимиты позже без миграций. |
| Что после отказа | Две кнопки: **«Отклонить»** — кулдаун `ACCESS_RETRY_DAYS` (деф. 7), потом можно подать заново; **«Забанить»** — навсегда, бот молчит. |
| Статистика в боте | `/stats` (сводка + топ) и `/stats <user>` (по человеку, с разбивкой по командам). |
| Приватность в базе | Содержимое не хранится вовсе: ни ссылок, ни заголовков, ни поисковых запросов, ни имён файлов. |
| Приватность в логах | Для всех, кроме админа: вместо `url` — только `host`; `title`, `query`, имя файла не пишутся (у файла — только расширение). Для админа лог подробный, как сейчас. |
| Привязка расхода к пользователю | **AsyncLocalStorage**: контекст запроса `{ requestId, userId, isAdmin }`, `complete()` пишет каждый платный вызов сам. |
| Хранилище | **SQLite через встроенный `node:sqlite`**, без новых npm-зависимостей. |

## Поведение

### Новый пользователь

Заявкой считается **любое** первое сообщение незнакомца (не только `/start` — люди сразу
кидают ссылку).

- Пользователю: «👋 Бот работает по приглашениям. Заявка отправлена владельцу — напишу, когда
  он ответит».
- Админу: «Новая заявка: Иван Петров (@ivanp), id 123456789» (без ника — «без ника») +
  кнопки **✅ Одобрить / ❌ Отклонить / 🚫 Забанить**.
- Пока заявка висит: на любое сообщение — «⏳ Заявка уже на рассмотрении», админу повторно
  ничего не приходит.

### Решение админа

- **Одобрить** → пользователю «✅ Доступ открыт!» + текущее приветствие `/start`.
- **Отклонить** → «Заявка отклонена. Повторить можно после <дата>». До даты на любое
  сообщение — эта же фраза, админу тишина. После даты — новое сообщение снова заявка.
- **Забанить** → пользователю ничего; дальше бот молча игнорирует любые его апдейты.
- Сообщение-заявка у админа редактируется в «✅ Иван Петров (@ivanp) — одобрен» (или
  отклонён / забанен), кнопки убираются.
- Повторное нажатие по уже обработанной заявке (двойной клик, старое сообщение) → ответ на
  callback «уже обработано», статус не меняется.

### Админ

- Задаётся `ADMIN_USER_ID` (обязателен). Всегда проходит доступ, не попадает под rate-limit.
- `ALLOWED_USER_IDS` теперь значит «одобрены заранее»: при старте эти id становятся
  `approved` (существующий статус `banned` не перетирается).
- Админские команды видны только админу (меню через `setMyCommands` со `scope: chat`),
  в `/help` их нет; от остальных — не существуют (сообщение идёт дальше как обычный текст).

| Команда | Что делает |
|---|---|
| `/users` | Списки: одобрены / ждут / отклонены / забанены — имя, @ник, id, дата. |
| `/stats` | Сегодня / 7 дней / 30 дней / всё время: запросы (из них ошибок), токены, $. Топ-5 по $ за 30 дней. |
| `/stats <id или @ник>` | То же по одному человеку + разбивка по командам (`summary`, `article`, `search`, `file`) + дата последнего запроса. Без содержимого. |
| `/revoke <id или @ник>` | Отозвать доступ = «Отклонить» (уведомление + кулдаун). |
| `/approve <id или @ник>` | Одобрить (в т.ч. разбанить или одобрить отклонённого). |
| `/ban <id или @ник>` | Забанить. |

## Данные

Один файл SQLite, `DB_PATH` (деф. `data/bot.db`). Схема создаётся при старте
(`CREATE TABLE IF NOT EXISTS`), версия схемы — `PRAGMA user_version` (на будущее). Режим
`journal_mode = WAL`. Время — Unix ms (INTEGER).

```sql
CREATE TABLE users (
  id           INTEGER PRIMARY KEY,          -- Telegram user id
  username     TEXT,                         -- без @, может быть NULL
  first_name   TEXT,
  last_name    TEXT,
  status       TEXT NOT NULL,                -- pending | approved | rejected | banned
  requested_at INTEGER,                      -- последняя заявка
  decided_at   INTEGER,                      -- последнее решение админа
  retry_after  INTEGER                       -- для rejected: когда можно снова
);
CREATE INDEX users_username ON users(lower(username));

CREATE TABLE requests (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id     INTEGER NOT NULL,
  command     TEXT NOT NULL,                 -- summary | article | search | file
  started_at  INTEGER NOT NULL,
  ok          INTEGER                        -- 1 / 0; NULL = не закрыт (упал процесс)
);
CREATE INDEX requests_user_time ON requests(user_id, started_at);
CREATE INDEX requests_time ON requests(started_at);

CREATE TABLE llm_calls (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  request_id        INTEGER NOT NULL REFERENCES requests(id),
  created_at        INTEGER NOT NULL,
  model             TEXT NOT NULL,
  prompt_tokens     INTEGER NOT NULL,
  completion_tokens INTEGER NOT NULL,
  cost_usd          REAL                     -- NULL = провайдер не сообщил
);
CREATE INDEX llm_calls_request ON llm_calls(request_id);
```

- «Запрос» для статистики — строка `requests` (одно действие пользователя), а не вызов LLM:
  статья по часовому видео — 1 запрос и 10–20 строк `llm_calls`.
- Запросы, упавшие до LLM (сайт не открылся), тоже пишутся — в них просто нет `llm_calls`.
- Ник и имя обновляются при каждом апдейте (люди их меняют; `/stats @ник` должен находить).
- Поиск по `@ник` — без учёта регистра. Ник в Telegram уникален, но может перейти к
  другому человеку: `touchProfile`, записывая ник, обнуляет его у других строк. Так в базе
  у каждого ника не больше одного владельца — актуального.

### Стоимость

- Для OpenRouter (хост `LLM_BASE_URL` — `openrouter.ai`) к запросу добавляется
  `usage: { include: true }` — просьба вернуть стоимость. Другим провайдерам поле **не**
  шлём: строгие (OpenAI) отбивают незнакомые параметры.
- Стоимость читается из `usage.cost`, если это конечное число ≥ 0; иначе `NULL`. Разбор
  толерантный: ни отсутствие поля, ни странный тип не ломают вызов.
- ⚠️ Формат ответа OpenRouter сверить по документации при реализации (из облачной песочницы
  openrouter.ai закрыт). Риск ограничен сбором стоимости — токены и запросы считаются всегда.
- В `/stats`: если в периоде есть вызовы без стоимости — «$ —» (или «$X + н/д», если часть
  известна). Бесплатные модели — честный `$0`.

### Периоды

«Сегодня», «7/30 дней» считаются в JS от полуночи по часовому поясу процесса (`TZ`); в SQL
уходят готовые границы в ms. В `.env.example` — `TZ=Europe/Moscow`.

## Архитектура

### Порядок middleware (`bot.ts`)

1. **`access`** (`middleware/access.ts`, заменяет `allowlist`): обновить профиль в `users` →
   `decideAccess` → пропустить / создать заявку и уведомить админа / ответить «на
   рассмотрении» / «отклонено до …» / молчать (бан). Callback-кнопки от не-админа — `answerCallbackQuery` без действий.
2. **`rateLimit`** — как сейчас, админ пропускается.
3. **Админские команды**: `const admin = bot.filter(isAdmin)`; `admin.command('users', …)` и т.д.
   Для остальных команды не существуют — апдейт идёт дальше.
4. **Кнопки заявки**: `admin.callbackQuery(/^access:(approve|reject|ban):(\d+)$/, …)`.
5. Остальные регистрации — без изменений (до `bot.on('message:text')`).

Апдейты без `from` (каналы и т.п.) — игнорируются.

### Изменения

- **`llm/complete.ts`**: флаг `usage.include` для OpenRouter; `mapUsage` достаёт `cost`;
  после успешного ответа — `recordLlmCall` для `currentRequest()` (если контекста нет —
  ничего не пишем). Ошибка записи → `warn`, вызов не падает.
- **`onLink` / `onArticle` / `onDocument` / `onSearch`**: запрос открывается в `requests` в
  начале обработки и закрывается с `ok` там, где сейчас пишется строка лога `request`;
  тяжёлая часть выполняется внутри `runInRequest`. В `SummarySource` — поле `command`
  (`summary` | `file`). Поля `url`/`title`/`query`/`file` в логах — через `sourceLogFields`.
- **`core/extractor.ts`**: логирует `url` — тоже через `sourceLogFields` (берёт `isAdmin`
  из `currentRequest()`; вне контекста — как для не-админа, то есть только host).
- **`commands.ts`**: у `BotCommand` флаг `admin?: true`; `renderHelp` пропускает админские;
  `setMyCommands` — дефолт (обычные) + `scope: { type: 'chat', chat_id: ADMIN_USER_ID }`
  (обычные + админские). Тест-сверка с `bot.ts` учитывает `admin.command('…')`.
- **`config.ts`**: `ADMIN_USER_ID` (обязателен), `DB_PATH` (деф. `data/bot.db`),
  `ACCESS_RETRY_DAYS` (деф. 7); `ALLOWED_USER_IDS` — «одобрены заранее».
- **Удаляются** `middleware/allowlist.ts` и `allowlist.test.ts`.
- **`package.json`**: `engines.node` → `>=22.13` (`node:sqlite` без флага).
- **`Dockerfile`**: `RUN mkdir -p /app/data && chown node:node /app/data` до `USER node`.
- **`docker-compose.yml`**: **именованный** volume `bot-data:/app/data` (а не `./data`):
  именованный том наследует владельца `node` из образа, bind-mount каталога хоста был бы
  root-ом и бот не смог бы писать. Бэкап — `docker compose cp bot:/app/data/bot.db .`.
- **`.gitignore` / `.dockerignore`**: `data/`. **`.env.example`**: `ADMIN_USER_ID`, `DB_PATH`,
  `ACCESS_RETRY_DAYS`, `TZ`.
- **Доки**: README (настройка, «сначала напиши боту `/start` сам», бэкап), AGENTS
  (подводные камни: контекст запроса, приватность логов, админские команды), PLAN (Этап 9).

## Ошибки и граничные случаи

- **База не открылась** при старте → понятное сообщение и выход (как при плохом `.env`).
  Без проверки доступа работать нельзя.
- **Ошибка записи статистики** посреди запроса → `warn`, пользователь получает ответ.
- **Ошибка записи в `users`** в `access` → пользователю «⚠️ Временная ошибка, попробуй позже»,
  `error` в лог; не пропускаем (fail closed). Админ проходит всегда.
- **Уведомление админу не доставлено** (админ ни разу не писал боту) → заявка сохранена,
  `error` в лог, видна в `/users`.
- **Уведомление пользователю о решении не доставлено** (заблокировал бота) → статус всё равно
  меняется, `warn`.
- **Процесс упал посреди запроса** → в `requests` остаётся `ok = NULL`; в `/stats` такие не
  считаются ни успешными, ни ошибками, но входят в общее число запросов.
- **Двойное нажатие кнопки** → «уже обработано».
- **`/stats @ник`, ника нет в базе** → «Не нашёл пользователя».

## Вне рамок

Лимиты (на пользователя и общий), выгрузка CSV, хранение содержимого запросов,
уведомления админу о каждом запросе, несколько админов.
